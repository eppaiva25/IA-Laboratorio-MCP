## Conhecimentos consolidados

O Git possui três áreas importantes para nosso fluxo:

Working Directory → Staging Area → Repository

Aprendemos que:

- git status mostra o estado atual.
- git diff mostra alterações fora do staging.
- git add coloca alterações no staging.
- git diff --staged permite revisar o próximo commit.
- git commit cria um ponto permanente no histórico.
- git restore pode descartar alterações ainda não confirmadas.
- git add -u pode preparar alterações e exclusões de arquivos já rastreados.
- git log --oneline permite acompanhar a evolução do laboratório.
- Arquivos Untracked não fazem parte do histórico até serem adicionados.
- Arquivos removidos que já eram rastreados aparecem como deleted.

## Etapa complementar da sessão — Exercício de rejeição com `git restore`

### Contexto

Após praticar a aceitação de uma alteração feita pelo Claude Code (`dd9b69d`), exercitamos o caminho oposto: rejeitar uma alteração proposital feita por um agente, usando `git restore`. O objetivo foi consolidar que **toda alteração por agente passa por uma decisão humana** antes de entrar no histórico.

### O que foi realizado

- Pedimos ao Claude Code para fazer uma alteração proposital no `README.md`, acrescentando uma frase claramente identificável como descartável.
- O Claude Code adicionou a frase ao final do arquivo, mantendo tudo o que existia antes.
- Rodamos `git status` para identificar que `README.md` constava como modificado no Working Directory.
- Usamos `git diff -- README.md` para revisar **qual** era exatamente a alteração pendente, ainda fora do staging.
- **Decidimos rejeitar a alteração** — ela não tinha valor para o histórico do laboratório.
- Usamos `git restore README.md` para descartar a alteração que estava no Working Directory.
- Confirmamos com `git status` que o repositório voltou a apresentar `nothing to commit, working tree clean`.
- Rodamos `git diff -- README.md` novamente e confirmamos que **não havia mais nenhuma diferença** em relação ao último commit.

### Por que a rejeição funcionou

A alteração do `README.md` foi feita pelo Claude Code, mas **nunca foi adicionada à Staging Area** (não rodamos `git add`).

Como ela estava apenas no Working Directory, `git restore README.md` conseguiu descartá-la diretamente, sem necessidade de `git restore --staged` em uma etapa anterior.

Esse é o caso mais simples de rejeição: alteração feita, mas ainda não promovida a staging.

### Conhecimentos consolidados nesta etapa

- Existem **dois caminhos complementares** para tratar uma alteração vinda de um agente de IA:
  - **Aceitar:** `git add <arquivo>` → revisar com `git diff --staged` → `git commit -m "..."`. A alteração entra no histórico.
  - **Rejeitar:** `git restore <arquivo>`. A alteração some do Working Directory e o arquivo volta ao estado do último commit.
- O **mesmo fluxo de revisão** usado para alterações humanas vale para alterações feitas por agentes: `git status` para entender, `git diff` para inspecionar, depois decidir.
- Quando a alteração está **só no Working Directory**, `git restore <arquivo>` resolve em um único comando.
- Quando a alteração **já foi para a Staging Area**, a ordem correta é:
  1. `git restore --staged <arquivo>` (tira do staging, mantém o conteúdo no Working Directory);
  2. `git restore <arquivo>` (descarta o conteúdo).
- Após uma rejeição bem-sucedida, `git status` deve voltar a `working tree clean` e `git diff -- <arquivo>` deve sair vazio.
- `git restore` neste exercício **descartou uma alteração ainda não commitada** — a frase proposital nunca chegou a fazer parte da história do repositório.

### Princípio reforçado

Nem toda alteração precisa ser aceita. O **caminho da rejeição é tão importante quanto o caminho da aceitação**, e ambos usam os mesmos comandos Git já consolidados. O agente propõe, mas **a decisão de incorporar uma alteração ao histórico sempre é humana**.
